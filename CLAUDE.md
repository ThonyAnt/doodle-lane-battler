# Doodle Lane Battler: project notes for Claude Code

Hackathon MVP. A one-lane battler where every unit is something the player draws. Ink is the price of a drawing and sets the unit's strength; a vision model only decides what kind of unit it is. See README.md for how to run it and the rules.

## Layout

- `index.html`: the whole client. The block between `/*SIM-START*/` and `/*SIM-END*/` is the pure match logic (stats, combat, bot, drawing fallback guess). Keep it free of DOM access.
- `server.js`: zero-dependency Node server (Node 18+). Serves the page, reads drawings via OpenAI (`POST /read`), and runs online rooms. It extracts and runs the SIM block from `index.html`, so rules exist in one place.
- `qrcode.js`: vendored QR library (MIT). Do not edit.
- `.env`: holds `OPENAI_API_KEY` (git-ignored). `.env.example` is the template.

## Doodle Duel (`/duel`)

- `duel.html`: live 2-player stickman fight with hand-drawn weapons and abilities. The block between `/*DUEL-START*/` and `/*DUEL-END*/` is the pure rules (item stats, physics, phases, bot). Keep it free of DOM access.
- `duel-server.js`: routes under `/duel/` (`read`, `room`, `events`, `act`), loaded by `server.js`. Server-authoritative at about 30 Hz over Server-Sent Events; clients send held buttons plus press counts with a sequence number. `GET /duel/events` with `&watch=1` joins as the big screen: it never takes a player's seat, and the only action it may send is `rematch`.
- Phases: draw (two items, 100 shared ink) -> count -> fight (90 s, 160 health; `ROUND_TIME` and `HP`, raised from 60 s and 100 so that a round between bots lasts about 41 s instead of 23 and overdrive fills well before anyone dies) -> end; first to 2 rounds. Item kinds: melee, ranged, bomb, shield, dash, heal. Tuning lives in `itemStats`.
- Animation: fighters are a keyframed skeleton in the style of `motion-review.html` (the owner's reference; Alan Becker / 火柴人联盟). Clips are data in `anim/*.js` registered with `ANIM.add`; `anim/core.js` samples them (spline interpolation, IK so limbs never stretch, body spin and somersault channels, painted slash trail) and `anim/README.md` is the authoring guide. Preview with `node tools/strip.js <clip> [frames] [out.png]` (needs Chrome) or open `/anim-lab.html`.
- Attacks are moves in the `MOVES` table inside the rules block (duration, hit or shot times, cancel time, next move). Each move has a clip of the same name whose marks must match; some have a `_b` alternate animation. The vision model returns a `style` for melee (blade, spear, hammer, fist, dual) and ranged (bow, gun, staff, hurl, akimbo) drawings; each style has its own move set and clip file. Melee styles chain a combo on repeated taps (for example blade1 -> blade2 -> blade3) with running, air and down+attack variants; ranged styles have a shot, quick follow-ups, an air shot and a charged shot. An empty slot fights with the fist set. `STYLE` holds per-style reach, damage and knockback multipliers. `node tools/check-anim.js` verifies clips against `MOVES`.
- Paired styles (`PAIRED`): `dual` is a one-handed weapon in each hand (dual1 front hand -> dual2 back hand -> dual3 -> dual4, plus `_run`, `_air`, `_up`), `akimbo` is two pistols (akimbo_shot, then akimbo_rapid and akimbo_rapid2 alternate back and front hand; `_air` and `_power` fire both). The reader is told to use them only when the drawing shows two separate similar weapons; `splitPair` (rules block) finds two stroke groups parted by a clear gap, which `localGuess` uses to guess the style and `setArt` uses to give each hand its own sprite (if the drawing does not split, both hands hold the whole drawing). In clips the back hand's weapon angle is the per-key channel `ang2` (default: just below the front weapon) with slash windows `trail2`; `ANIM.draw` takes `weapon2`, and `ANIM.smear` / `ANIM.trail` take a last argument for the back hand. A move may give `mz` or `mzs` to fire from somewhere other than the style's `MUZZLE`.
- Play modes: the page starts in `online` mode and offers two room modes (`startMatch(bot)`: Player vs Bot with the bot on the server, Player vs Player), where this device is the screen and phones or tablets are the controllers. The local modes (`setMode` with `bot`, `2p` or `practice`; the "On this device" buttons in the header, on the start screen and in the retro File menu) run the match in the page with the keyboard or touch buttons. The owner asked for both to stay available.
- Desktop overlay: `overlay/main.js` (Electron, a dev dependency; `npm run overlay`) opens a transparent, always-on-top, click-through window over the work area and loads `/duel?desk=1`. In that mode (`DESK` in `duel.html`, body class `deskmode`) the page is transparent, one game unit is a fixed number of screen pixels, the arena is as wide as the screen with no platforms (`createDuel({width,plats})`), health shows above heads, and the page tells the app via `window.overlayHost` when to take the mouse. `electron overlay/main.js --selftest=out.png` renders a frame off-screen. Window terrain: `overlay/windows.js` (koffi, Windows only, read-only) lists other apps' windows front to back and computes the visible parts of their top edges; `main.js` polls it every 100 ms and sends changes to the page, which converts them to platforms (`deskTerrain`) and calls `sim.setPlats`, or posts `{type:"plats"}` to the room when it is the big screen (only a watcher may; the server rebroadcasts a `plats` event). `setPlats` carries a fighter standing on a platform whose `id` persists. The header toggle "Draw here / Draw on tablets" (`drawHere`, `drawTablets`) switches any device between the ordinary game and being the big screen of a new room; in the overlay an online room uses the standard 960 stage scaled to the screen. The server itself still has no dependencies.

- Secondary motion: `anim/rig.js` (`ANIM.rig`) is a display-only spring layer over the clips, using the spring maths of his rig. `drawFighter` samples the clip as before, then `rig.apply` treats that pose as targets: each joint is a damped spring (stiffness per joint in `KM`), bones are pulled toward their lengths (`constrain`), planted feet are pinned, both arms and the weapon angle are pinned while `f.act` is set, and the output is blended by Jelly (0 = the clip pose, bit for bit). `rig.kick` throws the joints on a `hit` event (direction from the event's `dir`). `rig.ghost` / `drawGhosts` are the onion-skin afterimages (always with Onion skin on, otherwise only during a dash; the owner found them too much during attacks). Settings live in `ANIM.rig.P` (jelly 0.25, stretch 0.36, flab 0.4, exag 1 by default; saved in localStorage as `dd-rig`) and are driven by his Rig Properties sliders in `retroBuild`. `anim/core.js` reads two optional sample fields it sets, `s.bow` (limb curve) and `s.belly`. Every hook in `duel.html` checks `ANIM.rig`, so the page works without the file. The rules and the server never see any of this.

- Sound: `sfx.js` (`window.SFX`) synthesizes every effect with the Web Audio API; there are no audio files. `sfxHear` in `duel.html` plays one sound per game event and a few from the difference between two snapshots (swing, jump, landing, hack, countdown). A controller phone stays silent when the room has a big screen. The header's Sound button mutes it (`dd-sfx` in localStorage). The sounds were written without being listened to, so the mix is a first guess. The rules and the server never see any of this.
- Item stats: the reader returns `power`, `range`, `speed` (1 to 10) and two `traits`. `balanceStats` scales the three to a total of 15 (`STAT_BUDGET`), each 1 to 9, so only the proportions matter; `itemStats` turns them into multipliers (`LEAN`: power and speed are worth the same per point, so trading them does not change damage over time; range is paid for with damage). Ink still sets overall strength. Do not let the reader set the total.
- Traits live in `TRAITS` (which kinds may have each) and act in `hurt`, `projectiles` and `control`. `traitChoices` keeps the reader's two if they fit the kind and tops up from the rest.
- `validItem(reply, strokes)` never fails: an unknown kind is sorted by style, then by telling words (`KIND_HINTS`, `STYLE_HINTS`), then by the drawing's shape (`localGuess`), then defaults to melee.
- `S.tweak(side, slot, {kind, style, trait, tune})` changes a made item during the draw phase; online it is `POST /duel/act` with `type:"tweak"`. The sketchbook card (stats, trait choice, tuning, "Not right?") and the big screen's loadout panel both read `view.items`.
- Balance: `STYLE` damage numbers were tuned by a round-robin of the eight styles (equal stats, trait and ink; the bot plus steady button presses on both sides) until each won 46 to 54% overall. Individual pairings are still lopsided (spear beats fists, bow loses to staff). `dual` and `akimbo` were added afterwards with moves scaled from blade and gun; their `STYLE` damage was set with a rebuilt version of that simulation, which does not reproduce the original 46 to 54% for the old eight (it puts hammer near 64% and fists near 36%), so treat their numbers as a first guess. Quick follow-up shots have little or no stun so ranged weapons cannot stun-lock. Win rate in that simulation swings wildly on small damage changes (8% more damage wins about 85% of mirror matches), so it cannot judge stat leanings or the situational traits; those are balanced by construction, not measured.
- Input reliability: online clients resend their held buttons every 350 ms during a round, because one lost release request used to leave a fighter running; `releaseAll()` drops held directions when a round ends or the page loses focus. The drawing pad follows one pointer per stroke, lets a pencil take over from a touch, and ignores touches for 8 s after pencil use (palm rejection).
- Impact effects. Hit-stop is in the rules: a hit that staggers sets `S.stop` (0.03 to 0.1 s by damage, more for `fin`, the last hit of an `end` move or a charged shot) and `tick` freezes the whole fight, clock included, so it cannot change who wins; the snapshot carries `hs` and clients do not extrapolate while it is set. Hit events carry `w` (weight 0 to 1) and `fin`. The renderer does the rest: shake by weight, an impact frame for the ultimate only, when its last copy lands (hit events from it carry `ult`; the picture is inverted for about 460 ms as two flashes (`IMPACT_MS`, `impactOn`), because a white flash does not show on a white stage; the owner did not want ordinary attacks or knockouts to black the screen out), (afterimages are the spring rig's, dash only), and the hit fighter rattling and paling during the stop. `CALM` (the system's reduced-motion setting) turns the impact frame off and cuts the shake; the desktop overlay never gets the impact frame or the dimming.
- Slow, then fast: `ANIM.add` gives every clip with a hit or shot mark a `warp`, and `ANIM.sample` bends the clock before the first mark (`t = a*(t/a)^1.45`) so the wind-up lingers and the strike takes fewer frames. The pose at the mark and everything after it are as authored, so marks still match `MOVES`. A clip opts out with `punch:0`; `anim-lab.html?punch=0` shows the authored timing.
- Ultimates (`ULTS`, `S.startUlt`, `ultStep`, input `u`, key U, clips in `anim/ultimate.js`): a full overdrive bar can be spent on one instead of a hack, and every weapon style has its own. `ULTS[style]` gives the name, the casting move (`fleet`, `ult_slam`, `ult_rush`, `ult_dash`, `ult_shoot`, `ult_akimbo`; all have `ult:1` and a `cast` time) and a `kind` that `ultStep` acts on: blade `fan` (INK FLEET: copies of the drawing fan out overhead and fly in one by one, curving), spear `rain` (copies line up high over the foe and dive at wherever the foe is), hurl `ring` (copies circle the fighter and all go at once), staff `meteor` (one orb drops on the spot where the foe stood), hammer `quake` (leap, slam, a shock wave along the ground both ways; jump it; walls and crates stop it), fist `rush` (lunge and eight blows), dual `cross` (three blinks through the foe with a cut each), bow `pierce` (one huge arrow), gun `storm` (twelve bullets), akimbo `fire` (six shots forward and six back). Drawings that are not weapons use the blade's. All are worth `FLEET_DMG` (30) if everything lands, split evenly between the pieces, so they differ in shape and counterplay, not strength; that number is a guess and has not been through the balance simulation. Everything they hit with is marked `tr:'fleet'`: it does not refill the caster's bar, and its last hit (`fin`) is the only thing that triggers the impact frame. Once started, an ultimate always plays out (`casting` in the rules): the caster still takes damage but is not staggered, knocked back, flung, disarmed, recycled or counter-stunned out of it, cannot forge a new weapon or dash away by drawing, and the page never swaps its animation for a hit reaction. Only a knockout ends it early. The owner asked for this; before, a stunning hit before `cast` broke it off for half the bar. Copies waiting in formation are projectiles with `hover`. `min` / `max` in `ULTS` are the distances at which the bot will try each one. `node tools/test-world.js` casts every one.
- The ultimate is a cut scene (the owner asked that nothing can be done while one plays, and that it be very dramatic and slower). Rules: `ultLock()` is the side whose ultimate is playing, from `startUlt` until the casting move is over and no projectile with `tr:'fleet'` is left. While it is not -1, `tick` runs only the caster (`control`, with no input once the move itself is over) and the ultimate's own projectiles (`projectiles(dt, side)`); the other fighter, every other projectile, `world`, the spreadsheet script and the round clock are skipped, `setInput` swallows every press, and `S.stroke`, `S.startHack` and a second `startUlt` are refused. Damage lands at once; the last blow's knock-back is stored on the held fighter and plays when time starts again. `S.ult`, `S.ultT`, `S.ultDmg` track it; the snapshot carries `ul:[side, seconds]`, zeroes the held fighter's velocity and marks held shots `z:1` so clients do not extrapolate them; events `ult` (name, sub, slot, intro) and `ultend` (total damage). Pacing: `ULT_INTRO` (everything holds while it is announced), `ULT_RATE` (the casting move plays at 0.8 speed; clips untouched), `ULT_BEAT` (hit-stop after each blow) and `ULT_FINAL` (after the last). A whole ultimate takes about 3.8 s. Page: section "the ultimate, on screen" (`ultBack`, `ultFront`, `impactOn`): dark stage with light on the caster, letterbox bars with the name, a slanted name band with the drawing during the intro, streaks and rings, the held fighter in grey (`held` in `drawFighter`), the last blow as an impact frame (`impactFrame`: the picture is flattened to pure ink with a canvas filter and held as four pictures over 400 ms, white, black, white, black, with a jagged star, its outline, shards and force lines growing from the point of impact, slipped in under the figures with `destination-over` so they stay on top; two flashes, kept under three a second on purpose; the camera jolt comes when the frame ends), a small star pop on every other blow (`ultPops`), focus lines redrawn about eleven times a second (`focusLines`), and on the retro desktop a CSS blur of everything behind the fight (body class `ultdim`). The caster is not frozen during the announcement: the casting move creeps forward at `ULT_INTRO_RATE` until `act.intro` runs out. The owner found the first version janky and asked for stick-fight impact frames, and a ring burst when time starts again (the damage number over the fighter is the running total, `ultDmg`, which counts up as the blows land); body class `ultlock` greys the touch controller. The old ways out (jump the shock wave, double-jump the arrow, walk off the meteor's mark) are gone, and the bot's code for them is now idle.

- Bot (`makeBot`): its fighting looks at the match every tick but acts through limits set by skill `d` (0 to 1): a reaction time (0.30 to 0.06 s before it notices a move or a shot), a press rate (4.5 to 9 a second), moments of hesitation, and a chance of reacting to a threat at all. ## Online play

- `POST /room` creates a room with a 4-letter code. `GET /events?room=CODE&id=CLIENT` is a Server-Sent Events stream (`hello`, `players`, `state`, `pending`, `spawn`, `cancel`, `reset`, `gone`). `POST /act` takes `start`, `reset` and `send` (strokes plus a PNG of the pad).
- The server is authoritative: it owns ink, runs the sim at 20 Hz and broadcasts state at about 10 Hz. Clients send strokes; every client rebuilds unit sprites from those strokes.
- First client in a room is Blue (side 0), second is Red (side 1), later ones spectate. A client id in sessionStorage lets a player reload and keep their side.
- Rooms are in memory, so a deployment must be a single instance.

## Tuning numbers (all in the SIM block)

Base health 500, match 90 s, ink max 100, refill 6/s (12/s in the last 30 s), ink cost = stroke length / 28. Unit speed and health were raised/lowered once because the first version stalemated in about 90% of simulated matches. The bot's units are 15% weaker than their ink cost; that number is a guess.

- Tested: match rules by simulation; single-device modes and a full online match between two headless browsers, all against a stand-in for the OpenAI endpoint.
- Not tested: the real OpenAI API (accuracy and latency on doodles), real iPads and touch input, play over a slow network.
- The original default model `gpt-4.1-nano` was retired by OpenAI; the default is now `gpt-4.1-mini`, checked against the real API (about 1 s per drawing).
