# Doodle Lane Battler: project notes for Claude Code

Hackathon MVP. A one-lane battler where every unit is something the player draws. Ink is the price of a drawing and sets the unit's strength; a vision model only decides what kind of unit it is. See README.md for how to run it and the rules.

## Working rules

- Do not run the test suites (`tools/test-*.js`, `tools/check-anim.js`, `tools/balance.js`, `tools/net-bench.js`) unless the owner asks. After a change, say that they were not run and offer to run them.

## Layout

- `index.html`: the whole client. The block between `/*SIM-START*/` and `/*SIM-END*/` is the pure match logic (stats, combat, bot, drawing fallback guess). Keep it free of DOM access.
- `server.js`: zero-dependency Node server (Node 18+). Serves the page, reads drawings via OpenAI (`POST /read`), and runs online rooms. It extracts and runs the SIM block from `index.html`, so rules exist in one place.
- `qrcode.js`: vendored QR library (MIT). Do not edit.
- `.env`: holds `OPENAI_API_KEY` (git-ignored). `.env.example` is the template.

## Doodle Duel (`/duel`)

- `duel.html`: live 2-player stickman fight with hand-drawn weapons and abilities. The block between `/*DUEL-START*/` and `/*DUEL-END*/` is the pure rules (item stats, physics, phases, bot). Keep it free of DOM access.
- `duel-server.js`: routes under `/duel/` (`read`, `room`, `events`, `act`, and the WebSocket `ws`: see Netcode below), loaded by `server.js`. Server-authoritative at about 30 Hz over Server-Sent Events; clients send held buttons plus press counts with a sequence number. `GET /duel/events` with `&watch=1` joins as the big screen: it never takes a player's seat, and the only action it may send is `rematch`.
- Phases: draw (two items, 100 shared ink) -> count -> fight (90 s, 160 health; `ROUND_TIME` and `HP`, raised from 60 s and 100 so that a round between bots lasts about 41 s instead of 23 and overdrive fills well before anyone dies) -> end; first to 2 rounds. Item kinds: melee, ranged, bomb, shield, dash, heal. Tuning lives in `itemStats`.
- Animation: fighters are a keyframed skeleton in the style of `motion-review.html` (the owner's reference; Alan Becker / 火柴人联盟). Clips are data in `anim/*.js` registered with `ANIM.add`; `anim/core.js` samples them (spline interpolation, IK so limbs never stretch, body spin and somersault channels, painted slash trail) and `anim/README.md` is the authoring guide. Preview with `node tools/strip.js <clip> [frames] [out.png]` (needs Chrome) or open `/anim-lab.html`.
- Attacks are moves in the `MOVES` table inside the rules block (duration, hit or shot times, cancel time, next move). Each move has a clip of the same name whose marks must match; some have a `_b` alternate animation. The vision model returns a `style` for melee (blade, spear, hammer, fist, dual) and ranged (bow, gun, staff, hurl, akimbo) drawings; each style has its own move set and clip file. Melee styles chain a combo on repeated taps (for example blade1 -> blade2 -> blade3) with running, air and down+attack variants; ranged styles have a shot, quick follow-ups, an air shot and a charged shot. An empty slot fights with the fist set. `STYLE` holds per-style reach, damage and knockback multipliers. `node tools/check-anim.js` verifies clips against `MOVES`.
- Paired styles (`PAIRED`): `dual` is a one-handed weapon in each hand (dual1 front hand -> dual2 back hand -> dual3 -> dual4, plus `_run`, `_air`, `_up`), `akimbo` is two pistols (akimbo_shot, then akimbo_rapid and akimbo_rapid2 alternate back and front hand; `_air` and `_power` fire both). The reader is told to use them only when the drawing shows two separate similar weapons; `splitPair` (rules block) finds two stroke groups parted by a clear gap, which `localGuess` uses to guess the style and `setArt` uses to give each hand its own sprite (if the drawing does not split, both hands hold the whole drawing). In clips the back hand's weapon angle is the per-key channel `ang2` (default: just below the front weapon) with slash windows `trail2`; `ANIM.draw` takes `weapon2`, and `ANIM.smear` / `ANIM.trail` take a last argument for the back hand. A move may give `mz` or `mzs` to fire from somewhere other than the style's `MUZZLE`.
- Play modes: the page starts in `online` mode and offers two room modes (`startMatch(bot)`: Player vs Bot with the bot on the server, Player vs Player), where this device is the screen and phones or tablets are the controllers. The local modes (`setMode` with `bot`, `2p` or `practice`; the "On this device" buttons in the header, on the start screen and in the retro File menu) run the match in the page with the keyboard or touch buttons. The owner asked for both to stay available.
- Desktop overlay: `overlay/main.js` (Electron, a dev dependency; `npm run overlay`) opens a transparent, always-on-top, click-through window over the work area and loads `/duel?desk=1`. In that mode (`DESK` in `duel.html`, body class `deskmode`) the page is transparent, one game unit is a fixed number of screen pixels, the arena is as wide as the screen with no platforms (`createDuel({width,plats})`), health shows above heads, and the page tells the app via `window.overlayHost` when to take the mouse. `electron overlay/main.js --selftest=out.png` renders a frame off-screen. Window terrain: `overlay/windows.js` (koffi, Windows only, read-only) lists other apps' windows front to back and computes the visible parts of their top edges; `main.js` polls it every 100 ms and sends changes to the page, which converts them to platforms (`deskTerrain`) and calls `sim.setPlats`, or posts `{type:"plats"}` to the room when it is the big screen (only a watcher may; the server rebroadcasts a `plats` event). `setPlats` carries a fighter standing on a platform whose `id` persists. The header toggle "Draw here / Draw on tablets" (`drawHere`, `drawTablets`) switches any device between the ordinary game and being the big screen of a new room; in the overlay an online room uses the standard 960 stage scaled to the screen. The server itself still has no dependencies.
- InkShop merge (Alex's prototype, repo `al371160/hackprinceton-brainstorming-alex`, file `prototype/inkshop-duel.html`; our codebase is the base). On a wide fine-pointer screen (`RETRO`, off with `?plain=1`) the page is his InkShop desktop. His code is copied unchanged between `BEGIN verbatim` / `END verbatim` markers in three places: the `INK` block in the rules (geometry helpers, glyph templates `T`, `recognize`, `HACKS`), `inkshop.js` (effects, drawing helpers, tools, menus, `buildUI`) and `inkshop.css` (nested under `#inkos`); his markup is in `duel.html` inside `#inkos`. Do not edit inside the markers; re-copy from his file instead.
- Adapted from his code into the server-run rules (`createDuel`, section "InkShop world"): `S.stroke` -> grouping -> `recognize` -> `applyGlyph` (platform, wall, crate, block, shield, trap, arrow dash/fling/wind/link, erase, lightning, mid-fight weapon `forge`), `startHack` / `counterHack` / `execHack` / `patchCanvas`, `stepBody` props, `impact` slam damage. Drawn things keep his convention ({x,y}, y DOWN, floor at 0); fighters use ours (height above floor). New: the art board (`BOARD`, `boardCells`, `S.setLayout`), the mining move (`mine`, `mineHit`, key L), mid-fight `ink2` and `od` meters, inputs `m`, `q`, `h`. Shapes reach clients once as `obj` events with strokes; snapshots carry only ids and positions.
- The bot (`makeBot`) is our fighting logic plus his `AI.decide` / `onHack` / `Drawer` adapted (ghost cursor, glyphs, hacks, counters). Server acts added: `stroke` (players), `layout` (big screen only). `node tools/test-world.js` tests the world rules.
- Not merged: his fighter movement, pick-up weapon items, cursor grab.
- Secondary motion: `anim/rig.js` (`ANIM.rig`) is a display-only spring layer over the clips, using the spring maths of his rig. `drawFighter` samples the clip as before, then `rig.apply` treats that pose as targets: each joint is a damped spring (stiffness per joint in `KM`), bones are pulled toward their lengths (`constrain`), planted feet are pinned, both arms and the weapon angle are pinned while `f.act` is set, and the output is blended by Jelly (0 = the clip pose, bit for bit). `rig.kick` throws the joints on a `hit` event (direction from the event's `dir`). `rig.ghost` / `drawGhosts` are the onion-skin afterimages (always with Onion skin on, otherwise only during a dash; the owner found them too much during attacks). Settings live in `ANIM.rig.P` (jelly 0.25, stretch 0.36, flab 0.4, exag 1 by default; saved in localStorage as `dd-rig`) and are driven by his Rig Properties sliders in `retroBuild`. `anim/core.js` reads two optional sample fields it sets, `s.bow` (limb curve) and `s.belly`. Every hook in `duel.html` checks `ANIM.rig`, so the page works without the file. The rules and the server never see any of this.

Each move has a clip of the same name whose marks must match; some have a `_b` alternate animation. The vision model returns a `style` for melee (blade, spear, hammer, fist) and ranged (bow, gun, staff, hurl) drawings; each style has its own move set and clip file. - Sound: `sfx.js` (`window.SFX`) synthesizes every effect with the Web Audio API; there are no audio files. `sfxHear` in `duel.html` plays one sound per game event and a few from the difference between two snapshots (swing, jump, landing, hack, countdown). A controller phone stays silent when the room has a big screen. The header's Sound button mutes it (`dd-sfx` in localStorage). The sounds were written without being listened to, so the mix is a first guess. The rules and the server never see any of this.
- Item stats: the reader returns `power`, `range`, `speed` (1 to 10) and two `traits`. `balanceStats` scales the three to a total of 15 (`STAT_BUDGET`), each 1 to 9, so only the proportions matter; `itemStats` turns them into multipliers (`LEAN`: power and speed are worth the same per point, so trading them does not change damage over time; range is paid for with damage). Ink still sets overall strength. Do not let the reader set the total.
- Transformations ("transform" in the code; one of the planned customization axes): a melee or ranged item may carry one in `it.customs=[{id,...params}]`, set through `S.setItem` (in the spec) or `S.tweak(side,slot,{customs})` (online: `customs` in the `tweak` act) and cleaned by `transformValid`, which drops anything unknown and never throws. The table is `TRANSFORMS` (label, point cost, text): `twoform` (double-tap down switches to style `alt`), `split` (a landed finisher splits it into `dual` / `akimbo` for `secs`; a pair joins into one instead), `giant` (every `every` seconds the next move is twice the size and reach, slower), `evolve` (a stage per `hits` blows landed, three stages, starts small), `thrown` (melee throws itself beyond `far` and the shot returns; ranged is swung up close), `overgrown` (grows over `secs`, cut back when its holder is hit). How it works: the item keeps what it was made as (`k0`, `s0`) and `tfShape` rewrites its `kind`, `style` and `st` (always from `itemStats` with the item's own ink and stats) to the form in use, so moves, bots, the ultimate (`ultOf`) and the picture follow without special cases. Per-round state is on the fighter (`f.tf[slot]`, made lazily, so `fresh` resets it and `S.hash` covers it); `tfReset` in `resetWorld` puts the items back. A change of move set waits until the fighter is in no move; nothing changes while an ultimate plays. Hooks: `tfStart` (startMove), `tfStep` (control), `tfHurt` (hurt), `tfBuild` / `tfSpec` (buildItem, tweak), `tfView` (snapshot `items[][].tf`). The page: `tfSync` rebuilds the sprites when the style changes and eases the size, `tfDraw` (from `sprite`) draws the outline layers, glow and the flash of a change. `S.morph(side,slot,back)` forces one (practice only; the Transform row on `/moves`). Point costs and all numbers are first guesses, not measured.
- Traits live in `TRAITS` (which kinds may have each) and act in `hurt`, `projectiles` and `control`. `traitChoices` keeps the reader's two if they fit the kind and tops up from the rest.
- Attack-shape customizations (`SHAPES`, search the word "shape" in `duel.html`): prebuilt blocks that change how an item's shot or swing travels, meant to be picked per weapon by a model later (nothing calls a model yet). An item carries `it.customs=[{id,...params}]`, set with `S.shapeSet(side,slot,list)` (a logged command; the draw phase before ready, or any time in practice, like `S.tweak`, which keeps the list). `shapeFit(kind,list)` is the validator: unknown ids, blocks for another kind, repeats and anything past `SHAPE_MAX` (3) are left out, parameters are pulled inside `[least, most, default]`, and it never throws. Each block has a `cost` in points (a first guess, not tuned): ranged `split` 3 (three pieces at 55% each, 40% of the way along), `spiral` 2 (weaves 26 px either side, hit area a little taller), `linger` 3 (stops at the end of its range and hangs 2 s at 60% damage), `ricochet` 2 (3 bounces off floor, walls, ledges and solids, +20% damage and fresh range each), `swell` 2 (85% damage at the muzzle to 135% at full range, hit area grows); melee `echo` 3 (a ghost repeats each swing 0.5 s later where it was made, 50% damage, 0.12 s stun) and `shockwave` 2 (a finisher made on the ground sends a low wave 240 px, 40% damage; a jump clears it). Rules: `shapeFire` (called where `act` pushes a shot), `shapeSwing` (called in `act` after a move's hits), `shapeStep` (called first thing for a shot with `p.sh` in `projectiles`). State is `p.sh` and `p.hr` on shots and `shE` / `shW` on `f.act`; the echo and the wave are entries in `S.pr` (`st:'echo'`, `st:'swave'`), so `S.hash`, the ultimate's freeze and the round reset already cover them, and no dice are rolled. Ultimates' own shots never carry `p.sh`. The snapshot adds `sh` to a shot (from `shapeView`) and `cu` to an item; `shape` events mark a split, a bounce, a shot stopping or going off, and a wave leaving. Tells are drawn by `shapeUnder`, `shapeDraw` and `shapeFx`, accents in the owner's colour. The move tester has a Shape row (`labShape`) and a "Dummy behind" box so a shot can be watched to the end of its flight. Not done: no server act for it (online play cannot set one yet), nothing in the sketchbook card or loadout panel shows it, the bot does not know about any of it, and none of it has been balanced.
- `validItem(reply, strokes)` never fails: an unknown kind is sorted by style, then by telling words (`KIND_HINTS`, `STYLE_HINTS`), then by the drawing's shape (`localGuess`), then defaults to melee.
- `S.tweak(side, slot, {kind, style, trait, tune})` changes a made item during the draw phase; online it is `POST /duel/act` with `type:"tweak"`. The sketchbook card (stats, trait choice, tuning, "Not right?") and the big screen's loadout panel both read `view.items`.
- Balance: `STYLE` damage numbers were tuned by a round-robin of the eight styles (equal stats, trait and ink; the bot plus steady button presses on both sides) until each won 46 to 54% overall. Individual pairings are still lopsided (spear beats fists, bow loses to staff). `dual` and `akimbo` were added afterwards with moves scaled from blade and gun; their `STYLE` damage was set with a rebuilt version of that simulation, which does not reproduce the original 46 to 54% for the old eight (it puts hammer near 64% and fists near 36%), so treat their numbers as a first guess. Quick follow-up shots have little or no stun so ranged weapons cannot stun-lock. Win rate in that simulation swings wildly on small damage changes (8% more damage wins about 85% of mirror matches), so it cannot judge stat leanings or the situational traits; those are balanced by construction, not measured.
- Input reliability: online clients resend their held buttons every 350 ms during a round, because one lost release request used to leave a fighter running; `releaseAll()` drops held directions when a round ends or the page loses focus. The drawing pad follows one pointer per stroke, lets a pencil take over from a touch, and ignores touches for 8 s after pencil use (palm rejection).
- Impact effects. Hit-stop is in the rules: a hit that staggers sets `S.stop` (0.03 to 0.1 s by damage, more for `fin`, the last hit of an `end` move or a charged shot) and `tick` freezes the whole fight, clock included, so it cannot change who wins; the snapshot carries `hs` and clients do not extrapolate while it is set. Hit events carry `w` (weight 0 to 1) and `fin`. The renderer does the rest: shake by weight, an impact frame for the ultimate only, when its last copy lands (hit events from it carry `ult`; the picture is inverted for about 460 ms as two flashes (`IMPACT_MS`, `impactOn`), because a white flash does not show on a white stage; the owner did not want ordinary attacks or knockouts to black the screen out), (afterimages are the spring rig's, dash only), and the hit fighter rattling and paling during the stop. `CALM` (the system's reduced-motion setting) turns the impact frame off and cuts the shake; the desktop overlay never gets the impact frame or the dimming.
- Slow, then fast: `ANIM.add` gives every clip with a hit or shot mark a `warp`, and `ANIM.sample` bends the clock before the first mark (`t = a*(t/a)^1.45`) so the wind-up lingers and the strike takes fewer frames. The pose at the mark and everything after it are as authored, so marks still match `MOVES`. A clip opts out with `punch:0`; `anim-lab.html?punch=0` shows the authored timing.
- Arena customizations (`ARENAS`, section "arena customizations" in the rules block; one of nine axes of weapon customizations a model will later pick from, no model wired in yet). An item may carry one block, `it.customs=[{id,secs}]`, set with `S.arenaSet(side,slot,list)` (draw phase or practice, like `S.tweak`; junk in never throws, an unknown id leaves no block; it returns the kept list with each entry's point cost from `arenaCost`). The holder sets it off on purpose: a melee finisher or charged shot that lands unblocked (the `fin` hit in `hurt`), a bomb or dash that hits, a shield or heal being used (`arenaUse` in `use`); then that weapon cools for `ARENA_CD` 9 s (`f.acd`). `S.arena` is the one effect running: a new one replaces it unless it is younger than `ARENA_HOLD` 1.2 s, when the new one is refused and keeps its cooldown. `arenaStep` runs at the end of an ordinary tick, so effects wait during an ultimate and hit-stop, and it skips a casting fighter. Blocks and first-guess costs (not tuned): gust 4 (wind away from the holder: carries fighters 110 px/s on the ground and 180 in the air, bends shots, shoves crates), moon 2 (half gravity for fighters and lobbed things), night 3 (display only: dark stage, a light of 230 px round the holder and 84 round the foe), rain 2 (slow status for anyone with nothing overhead, puts out burns), quake 3 (four jolts 1.3 s apart with a 0.5 s cue; whoever stands on anything is hopped and staggered 0.28 s, so jump the jolt), ring 4 (walls slide in to a 380 px pen round the fight, hold, slide back; shots stop at them). The snapshot carries `ar` (null in a match with no blocks): `it` ids per item, `rd` seconds until ready, `on` the running effect. On screen (`arenaBack`, `arenaFront`, `arenaEvent`): everything is in the holder's colour, a ring bursts from the weapon, a corner plate names effect and weapon with a draining bar, and the hand shows a turning star (ready), a filling ring (cooling) or a double ring (running). Everything is clipped to `arenaBox` (the art board, the sheet, or the view). On the desktop overlay night draws no darkness and ring no tint. `/moves` has "Arena block" and "Set off now" rows (`S.startArena`, practice only). Not done: no server act for `arenaSet`, nothing on the sketchbook card, bots do not know about the effects.
- Ultimates (`ULTS`, `S.startUlt`, `ultStep`, input `u`, key U, clips in `anim/ultimate.js`): a full overdrive bar can be spent on one instead of a hack, and every weapon style has its own. `ULTS[style]` gives the name, the casting move (`fleet`, `ult_slam`, `ult_rush`, `ult_dash`, `ult_shoot`, `ult_akimbo`; all have `ult:1` and a `cast` time) and a `kind` that `ultStep` acts on: blade `fan` (INK FLEET: copies of the drawing fan out overhead and fly in one by one, curving), spear `rain` (copies line up high over the foe and dive at wherever the foe is), hurl `ring` (copies circle the fighter and all go at once), staff `meteor` (one orb drops on the spot where the foe stood), hammer `quake` (leap, slam, a shock wave along the ground both ways; jump it; walls and crates stop it), fist `rush` (lunge and eight blows), dual `cross` (three blinks through the foe with a cut each), bow `pierce` (one huge arrow), gun `storm` (twelve bullets), akimbo `fire` (six shots forward and six back). Drawings that are not weapons use the blade's. All are worth `FLEET_DMG` (30) if everything lands, split evenly between the pieces, so they differ in shape and counterplay, not strength; that number is a guess and has not been through the balance simulation. Everything they hit with is marked `tr:'fleet'`: it does not refill the caster's bar, and its last hit (`fin`) is the only thing that triggers the impact frame. Once started, an ultimate always plays out (`casting` in the rules): the caster still takes damage but is not staggered, knocked back, flung, disarmed, recycled or counter-stunned out of it, cannot forge a new weapon or dash away by drawing, and the page never swaps its animation for a hit reaction. Only a knockout ends it early. The owner asked for this; before, a stunning hit before `cast` broke it off for half the bar. Copies waiting in formation are projectiles with `hover`. `min` / `max` in `ULTS` are the distances at which the bot will try each one. `node tools/test-world.js` casts every one.
- The ultimate is a cut scene (the owner asked that nothing can be done while one plays, and that it be very dramatic and slower). Rules: `ultLock()` is the side whose ultimate is playing, from `startUlt` until the casting move is over and no projectile with `tr:'fleet'` is left. While it is not -1, `tick` runs only the caster (`control`, with no input once the move itself is over) and the ultimate's own projectiles (`projectiles(dt, side)`); the other fighter, every other projectile, `world`, the spreadsheet script and the round clock are skipped, `setInput` swallows every press, and `S.stroke`, `S.startHack` and a second `startUlt` are refused. Damage lands at once; the last blow's knock-back is stored on the held fighter and plays when time starts again. `S.ult`, `S.ultT`, `S.ultDmg` track it; the snapshot carries `ul:[side, seconds]`, zeroes the held fighter's velocity and marks held shots `z:1` so clients do not extrapolate them; events `ult` (name, sub, slot, intro) and `ultend` (total damage). Pacing: `ULT_INTRO` (everything holds while it is announced), `ULT_RATE` (the casting move plays at 0.8 speed; clips untouched), `ULT_BEAT` (hit-stop after each blow) and `ULT_FINAL` (after the last). A whole ultimate takes about 3.8 s. Page: section "the ultimate, on screen" (`ultBack`, `ultFront`, `impactOn`): dark stage with light on the caster, letterbox bars with the name, a slanted name band with the drawing during the intro, streaks and rings, the held fighter in grey (`held` in `drawFighter`), the last blow as an impact frame (`impactFrame`: the picture is flattened to pure ink with a canvas filter and held as four pictures over 400 ms, white, black, white, black, with a jagged star, its outline, shards and force lines growing from the point of impact, slipped in under the figures with `destination-over` so they stay on top; two flashes, kept under three a second on purpose; the camera jolt comes when the frame ends), a small star pop on every other blow (`ultPops`), focus lines redrawn about eleven times a second (`focusLines`), and on the retro desktop a CSS blur of everything behind the fight (body class `ultdim`). The caster is not frozen during the announcement: the casting move creeps forward at `ULT_INTRO_RATE` until `act.intro` runs out. The owner found the first version janky and asked for stick-fight impact frames, and a ring burst when time starts again (the damage number over the fighter is the running total, `ultDmg`, which counts up as the blows land); body class `ultlock` greys the touch controller. The old ways out (jump the shock wave, double-jump the arrow, walk off the meteor's mark) are gone, and the bot's code for them is now idle.
- Customizations ("code on the fly" blocks; only the axis "effect on the wielder" is built). `CUSTOMS` in the rules block is a table of prebuilt behaviours a weapon can carry, each with a visible tell; the long comment above it is the authoring guide (how to add one, the moments, the context object). An item's blocks are `it.customs=[{id, params:{...}, when?, cost?}]` (snapshot: `items[side][slot].cu`), cleaned by the one validator `fitCustoms(list, kind, style)`: known ids that suit the kind, at most `CUSTOM_MAX` (2), parameters clamped, total `customPoints` within `CUSTOM_BUDGET` (10), never throws. Big blocks cost 5.5 to 7.5 and small ones 2.5 to 4.5, so a weapon gets one big one, or a big and a small one. Set them with `S.setCustoms(side, slot, list)` or `S.tweak(side, slot, {customs})` (draw phase, or any time in practice; online `POST /duel/act` `type:"tweak"` with `customs`); `validItem` passes a reader's `customs` through the validator, but nothing asks the reader for them yet.
  - How they run: each block has handlers `on:{tick, move, use, swing, shot, hit, struck, landed, took, jump, land, round, mote}`, called by `cfire(moment, fighter, slot, arg)` in `createDuel` with a context from `cuCtx` (`c.me`, `c.foe`, `c.p`, `c.st`, `c.emit`, `c.mote`, `c.shot`, `c.hurt`, `c.heal`, `c.free`, `c.rand`). Per-fighter state is `f.cu[id+slot]` (new every round with `fresh`, and when the item's `ver` changes; part of `S.hash` because every fighter field is). `f.run` and `f.grav` are per-tick multipliers a block may set. `S.motes` are free-flying things a block makes (lifesteal's orbs; snapshot `mo`, hashed, cleared with the shots). Nothing fires while an ultimate plays or for a casting fighter, and an ultimate's blows trigger nothing. A handler that throws is caught and noted in `S.cuFault`. `customWhen` / `customPay` and the tables `CUSTOM_WHEN` / `CUSTOM_COST` are empty places for a trigger and a cost on an entry (`when`, `cost`); they always say yes.
  - On screen: `TELLS[id]` in the page (before `drawFighter`): `back` / `front` (per fighter each frame, from the block's `view()` value in snapshot `f[side].cv[id]`), `weapon` (scale of the held sprite), `tint`, `fx` / `event` (events `{e:'cu', c:id, k:name, ...}`, with `snd` naming a sound), `mote`.

- Determinism (branch `replay-determinism`). A match is exactly repeatable from its seed and its commands. `createDuel({seed})` builds a mulberry32 generator `S.rand()` (`S.seed`; picked from `Math.random` when not given) and nothing in the rules block calls `Math.random` while a match steps. The shared helpers `rand` and `pick` (in `INK`) roll the block-level `RNG`, which a match points at its own generator only for as long as it steps or takes a command (`own` in `createDuel`) and a bot for as long as it thinks; it is put back afterwards, so page code that uses those helpers (`inkshop.js` particles, the glyph buttons) never uses up a match's numbers. `makeBot(side, skillOf, seed)` and `botLoadout(seed)` have generators of their own. `S.tickN` counts the 1/120 s ticks played; `S.ticks(n)` plays exactly n.
- Command log. With `createDuel({record:true})` every command from outside is logged as `[tickN, name, args]` (commands land between ticks). `S.log()` returns `{v:1, seed, opts, cmds, ticks}` (`ticks`: how long the match has run; `full:true` if the recording hit `LOG_ROOM`, about 2 MB, and stopped). `replayDuel(log, {untilTick}?)` makes the match again and gives the commands back at their ticks; the match it returns also has `S.seek(tick)` to play on (forward only) and `S.total`. The bot is never run in a replay: its presses and strokes are in the log. Two commands are packed: `setInput` is logged only when it changes a held button or a press count, as `[side, {changed buttons}]`, and `stroke` as `[side, [[x,y],...], colour]` (`S.stroke` rounds its points to 0.1 for this). While recording, a command is carried out with its arguments as they went into the log (through JSON), so the match and the replay are given the same thing. **Every new outside-facing `S.` method that changes the match must be added to `COMMANDS`**, or it is neither recorded nor given the match's dice; anything that pokes a match's state directly (the move tester does) is not in the log. State in closures (`S.effects[].end`, ultimate projectiles' `own`) is rebuilt by re-running commands, never copied.
- `S.hash()` is an FNV-1a fingerprint (8 hex digits) of the phase, clock, round, wins and every number of every fighter and projectile, to 0.01. A replay that ends with the same hash as the match is exact. `fnv1a(text)` is also the rules stamp: `/duel/replay` sends `rules` (the hash of the rules block's text) and the page works out its own (`rulesOf`, `RULES_HERE`).
- Rooms record. `GET /duel/replay?room=CODE` answers `{log, art, hash, rules}` (`art`: every drawing the room showed, by item version `ver`, so a replay can show the same pictures; `hash`: the match's state when the log was taken; `previous:true` when it is the match before the one being set up) or 404. A match replaced by a rematch, or whose room closes, goes on a shelf (`replayShelf` in `duel-server.js`: 30 minutes, 50 at most).
- Replay viewer: `duel?replay=CODE` (`REPLAY`, `setReplay`, `playReplay(log, extra)`, `replayShow`, `replayTick`; always the plain layout). It re-simulates in the page with `replayAt(log, tick)` and feeds every snapshot through `accept()`, so drawing and sound are the game's own; going back re-simulates from the first tick. It refuses a log whose `v` or `rules` differ, and warns if the replay does not end with the server's `hash` (different browser arithmetic would do that; not seen so far, only Node and the pretend browser have been tried).
- Knockout replay: `accept()` ends with `koNote(ko, v, viewAt, WINS)`, which keeps 5 s of snapshots and notes a knockout that does not end the match. `frame` sets `koView` from `koReplayFrame(ring, koMs, sinceKoMs)` (null for 0.4 s, then for 3 s the last second before the knockout at a third speed) and `render` draws `koView||view` under a REPLAY banner; sound is off meanwhile, the health bars follow what is drawn. `?ko=0` (`KO_ON`) switches it off; it is off in the replay viewer.
- The page's replay logic that needs no screen sits between `/*PAGE-PURE-START*/` and `/*PAGE-PURE-END*/` (after the rules block) and is loaded by `tools/test-replay.js`, like the rules. Keep it free of the DOM. `node tools/test-replay.js` covers seeds, the hash, the log, a real room on a child server (port 3193, about 15 s of real time for one round), the viewer and the knockout replay; for the last two it runs the whole page script in a pretend browser (`fakePage`), which catches errors but sees no pixels.
- `tools/balance.js --seed=N` plays round i of every pairing with seed N+i and players made afresh from derived seeds, so a run repeats exactly and two versions can be compared on identical rounds. Its numbers are not comparable with unseeded ones: without `--seed` the same bots play every round of a pairing and still hold the last round's shot ids in `seenShot` (each round is a new match that numbers shots from 1), so from round two they react to every shot with no reaction time. That makes ranged look weaker than in a real match: `quick` gives melee-beats-ranged about 53% unseeded and about 41% seeded, sword+bow against a sword about 55% and about 85%. The balance figures in the notes above came from the unseeded bench.
- Customizations, axis "what it leaves behind" (search for "leaves"; branch `otf-leaves`, one of nine axes built side by side, to be joined under a common framework). An item carries `it.customs=[{id,size,secs,cost}]` (kept through `buildItem` and `S.tweak`, shown in the snapshot as `items[..].cu`). `S.leaveSet(side,slot,list)` sets it while drawing or in practice (it is in `COMMANDS`); `leaveCustoms(list,kind)` never throws and drops unknown ids, ids the kind cannot carry, repeats and anything past `LEAVE_MAX` (2); `size` and `secs` are held to 0.6..1.5 and scale the cost. The blocks are the `LEAVES` table (name, point cost, kinds, numbers, blurb); costs are first guesses, never simulated: `fire` 4 (a melee swing lays flames in front, a shot lights the ground under its path, a bomb where it bursts; 4 damage a second to the foe standing in them, through the `burn` status), `slick` 2 (a hit or a landing leaves a puddle; anyone on it has a tenth of their footing, `leaveGrip` in `control`), `mine` 3 (every third attack move drops one at the feet; armed after 0.5 s, 9 damage, three at most), `spikes` 3 (the last blow of an `end` move, or a landing; up after 0.3 s, 6 damage and a pop-up, again every 0.9 s), `wall` 4 (a finishing blow that lands, or a charged shot: a wall just behind the foe, 4 s), `step` 1 (ranged only: a shot that hits nothing leaves a platform where it ran out, if 40 or more above the ground), `cloud` 2 (a hit or a landing; drawn over the fighters so it hides them, and keeps the foe `slow`, which is also "soaked" for the elements).
- Leaves, how they work. Flames, puddles, mines, spikes and clouds are `S.lv` (`{id,lq,k,side,x,y,w,life,max,t,cd}`, `y` a height above the floor); walls and steps are ordinary `S.objs` made with `addObj` and marked `leaf` with the owner's side, so the page draws, and players mine and erase, them like drawn ones. Hooks: `leaveAttack` (in `startMove`), `leaveSwing` (both exits of a melee hit mark in `act`), `leaveLand` (once for every shot or bomb that ends, just before `projectiles` filters them; it works out from where the shot is whether it ended on the foe, in a solid, on the ground or in the air), `leaveStep` (after `world` in `tick`). A new piece touching one of the same kind and owner joins and renews it (`leavePut`). One fighter has at most `LEAVE_CAP` (6) things out, objects included; the oldest goes. Flames, mines, spikes and the soaking act on the owner's foe only; the puddle on both. An ultimate leaves nothing (`tr:'fleet'`), and `leaveStep` is not run while one plays, so a caster is never interrupted. Works unchanged on the spreadsheet stage (things drop when what they lay on is deleted). `S.lv` is emptied in `resetWorld` and covered by `S.hash` (`leaveState`); the snapshot carries `lv`, rows of `[id,kind,owner,x,y,width,seconds left,0..1]`. Page: `leavesDraw(v,now,front)`, called in `render` after `worldBack` and again after the fighters for clouds. `/moves` has a "Leaves behind" row (`labLeaves`). Not done: no model or bot picks them, there is no `leaveSet` act on the server for online rooms, the tablet strip does not draw `lv`, and none of it has been through the balance bench. Tests are at the end of `tools/test-world.js`.
- Bot-vs-bot simulation gives a median round of about 22 s; melee wins most often between bots. Not tested on real tablets.

## RuleForge (match rules written by a model, Doodle Duel only)

Once both sides of a match have an item, a language model writes up to three small rules for how those items meet; each is proven in test fights and loaded into the live match. Plan and design: `docs/superpowers/plans/2026-11-14-rule-forge.md`.

Files:
- `forgescript.js`: the rule language, a strict subset of JavaScript. `ForgeScript.parse / check / compile / LIMITS / Fault`. UMD: the server requires it, the page loads it as `/forgescript.js`.
- `duel.html`, rules block: `FORGE_API` (everything a rule can name, per event: the one source for the checker, the sim's host object and the prompt), `FORGE_LIMITS`, and in `createDuel`: `S.addRule`, `S.rules`, `S.clearRules`, `S.sane`, `S.setHold`, `fireRules`, events `rule` and `rulefault`. The block must not name `ForgeScript`: compiled rules are handed in as functions.
- `forge.js` (Node): `buildPrompt`, `parseReply`, `verifyRule`, `fallbackRules`, `install`, `forgeRules` (generate, verify, repair once, fall back; memory cache), `dump` / `load` / `known` (the disk cache), `cleanName`, `cleanItems`, `itemsOf`, `keyOf`; statics `openai` (the model call) and `keep` (the cache file).
- `duel-server.js`: `scheduleForge(room)` after every item change (400 ms later, an item on each side), `room.forge={key,gen,state,rules}`, SSE event `forge` (`{state:'working'}`, `{state:'done',ms,rules}`, `{state:'idle'}`; replayed to a device that connects later), `POST /duel/forge` for matches simulated in the page (one request per 2 s per address), `forge-cache.json`.
- `duel.html`, page: the block between `/*FORGE-UI-START*/` and `/*FORGE-UI-END*/` is pure and run by the tests (`forgeCards`, `forgeTyped`, `forgeLine`, `forgeCallout`, `forgeInstall`, `forgeItems`, `shotOwner`); after it `setForge`, `forgeTick`, `localForge`. The window is `retroWindow('forge','FORGE.EXE',...)`, its styles are at the end of `inkshop.css`.
- `tools/test-forge.js` (everything above; child servers on port 3191), `tools/fake-openai.js` (the stand-in for the model; run on its own it is a model with one joke), `tools/forge-warm.js` and `tools/forge-live.js` (need the key; `tools/forge-env.js` is their shared setup).

The four events. A rule is for one ordered pair of items: `a` (its holder is `me`) and `b` on the other side.

| `on` | When the sim runs the rule | `a` must be |
| --- | --- | --- |
| `swat` | a foe projectile from `b` is inside my swing (see `swatting`) | melee (`b`: ranged or bomb) |
| `guard` | a foe projectile from `b` touches me while my shield from `a` is up, before the normal block | shield (`b`: ranged or bomb) |
| `strike` | my hit with `a` is about to land on the foe, who holds `b`; in `hurt()`, after the element match-up, before the block test | melee, ranged, bomb or dash |
| `near` | every 0.25 s of the fight while I hold `a`, the foe holds `b` and we are within 260 px | any |

An ultimate never triggers a rule; a projectile triggers shot rules once in its life.

Limits the sim enforces whatever the code asks for (`FORGE_LIMITS`):

| What | Limit |
| --- | --- |
| `shot.reflect` / `shot.slow` / `shot.power` / `hit.scale` | 0.5 to 1.5 / 0.3 to 1 / 0.5 to 1.5 / 0.6 to 1.4 |
| `shot.turn` | -180 to 180 degrees |
| `push` | 520 px/s each way |
| `burn`, `soak` / `stun` | 2 s a call / 0.6 s a call, 1.5 s per rule per round |
| `heal`, `hurt` | 8 hp a call, 24 hp per rule per round (a rule's fire included) |
| cooldown / `say` | 0.25 to 5 s / 18 characters, one per rule per 1.5 s |
| faults / countdown hold | 3 switch a rule off / 4 s |
| code | 800 characters, 250 nodes, 2000 steps a run |

Rules to keep:
- A rule's code is text from a model. It may only be parsed, checked and interpreted by ForgeScript: never `eval`, `new Function`, `vm`, a timer string or a script tag, on the server or in the page. Rule names, blurbs, code and item names are escaped (`fesc`) before they become HTML.
- A run "fires" (cooldown, `rule` event, call-out) only if it called an effect. An effect stopped by the spent round budget does not count, and neither does a `say` or `spark` in that same run. A returned shot can hit at once (`safe` 0).
- `verifyRule` runs its test fights with `Math.random` replaced by a fixed sequence, so a verdict is repeatable. Its staging is described above `scenarios` in `forge.js`.
- A room's forge carries a generation number: when an item changes, the rules of the old items are cleared at once and a forge still running for them installs nothing.
- The cache key (`keyOf`) is the cleaned name, kind, style, element, trait and the three stats of each item: a tuned or recoloured item is a different key. Only results with a model-written rule are kept on disk, and they are verified again when first used.
- In test fixtures give items a fixed trait (`traits:['swift'],trait:'swift'`): by name a Sword gets Lucky and a Ball gets Boomerang. A practice sim heals both fighters once `f.rest` passes 1.5 s. A landed swing starts a hit-stop during which nothing moves.

Tried with two real models (a small and a mid-sized one, given only the prompt for eight item sets: all 48 rules passed every check; fixtures in `tools/fixtures/forge-models/`, test `tools/test-forge-models.js`), but not with the OpenAI model the server asks by default. Unknown until someone runs `node tools/forge-live.js` with the key: whether the model writes valid ForgeScript from this prompt, how long it takes, whether the rules are funny, and whether `max_tokens: 700` and `response_format: json_object` suit the model chosen. The `FORGE.EXE` window, the call-outs and the "Forging rules..." banner were written without a browser; their logic is tested in Node, their look is not.

## Netcode: the WebSocket link (Doodle Duel only, off by default)

Branch `netcode-ws`, plan `docs/superpowers/plans/2026-11-14-netcode-ws.md` (its Task 6, the jitter buffer, was not built: the page still draws from the newest state, extrapolated by its age, exactly as on the event stream).

- **Switch.** The event stream (`GET /duel/events` plus `POST /duel/act` for every input) is still the default. `?net=ws` in the page address makes the page use a WebSocket (`/duel/ws?room=CODE&id=CLIENT[&watch=1]`) and fall back to the event stream if the socket has not opened within 1500 ms, closes, or says nothing for four seconds (a room sends its state at least four times a second, so that is a dead link the browser has not noticed: `LINK_SILENT_MS`, found silent on two looks a second apart); `?net=ws-only` never falls back and tries the socket again a second later (for tests). `NOWS=1` on the server leaves the socket off. A big screen opened with `?net=` puts it in the join link and QR code.
- **`ws.js`** is the WebSocket, written from RFC 6455 with `http` and `crypto` only: `encodeFrame`, `createDecoder` (fragments joined, 1 MiB limit, unmasked client frames refused), `acceptKey`, `attach(server, path, onSocket, {pingMs, maxBuffered})` (ping every 15 s, a socket that misses two pongs is dropped, as is one with 4 MiB waiting to go out) and `connect(url)`, a minimal client for tests and the bench.
- **`wire.js`** (UMD: `require` on the server, `window.Wire` in the page) knows nothing about snapshots. `createCodec()` packs any JSON value: a tag byte, zigzag varints for integers, numbers with one to three decimals as a scaled integer when that is exact (else float64), strings by a per-connection dictionary after first use. `diff(prev, cur)` / `apply(prev, patch)`: objects by field (field order is kept), lists whose members all have an `id` by id (the shots), lists of the same length place by place, any other list whole. `createSender()` / `createReceiver()` make and read state frames.
- **State frame.** Byte 0 is `1` (whole snapshot) or `2` (delta); then varints: the frame's number, for a delta the number of the snapshot it patches, and the server's clock in ms; then one packed value (the snapshot, or the patch, `null` for no change). A delta is against the newest snapshot the device has acknowledged, if it is among the last 32 sent; otherwise, and every 2 s anyway, the frame is whole. The page acknowledges the first frame, then every third (`{"t":"ack","ack":n}`), and with every input.
- **Everything else on the socket is text.** Down: every named event as `{"ev":name,"data":...}`. Up: `{"t":"input","seq":n,"ack":m,...buttons}`, `{"t":"ack","ack":m}`, and `{"t":"ping","ms":x}` answered with the event `pong` (the page times the round trip with it and does not pass it on). All other acts stay on `POST /duel/act`.
- **One place sends.** In `duel-server.js`, `tell(client, event, data)` is the only function that writes to a device, on either link; `broadcast` loops over it. `enter(room, id, watch, link)` and `leave(room, client)` are shared by both links, so a late device is told the same on both (items, `plats`, `forge`, state) and an event added by another feature needs no socket code. `takeInput` is shared too: only a higher `seq` counts, and the room loop still releases a direction it has not heard about for 0.9 s (`room.heldAt`). A second socket with the same id replaces the first (reload, or a tablet waking up) and gets a whole frame.
- **The page.** The link code is between `/*NET-PURE-START*/` and `/*NET-PURE-END*/` in `duel.html` (`chooseLink`, `openLink`, `linkMeter`, `linkText`): no DOM, the browser's `WebSocket` and `EventSource` are passed in, so `tools/test-net.js` runs it with stand-ins and against a real server. `joinRoom` collects the handlers (`on(name, fn)`) and hands them to `openLink`; `net.line` is the link, `net.link` is `'ws'`, `'sse'` or `''`. `sendInput()` writes to the socket at once when `net.link==='ws'`, else it is the old one-request-at-a-time code; the 150 ms repeat is unchanged. The receiver hands `accept()` its own copy of each snapshot (`accept` marks the events it is given). The desktop status bar shows link, round trip, jitter and kB/s; with `?net=` a player's badge shows the link.
- **Measured.** A recorded fight between two bots, 600 snapshots: 1,084,227 bytes of JSON, 46,060 bytes of packed deltas (4.25%); as frames with acknowledgements two frames late, 5.7%. `node tools/net-bench.js --delay=30 --jitter=20` measures press-to-movement time and bytes a second on both links through a relay that delays packets (about 9 minutes; the README has the table): with 30 ms + up to 20 ms each way, median 105.8 ms on the event stream against 92.4 ms on the socket, 95th percentile 175.1 against 110.1 ms, 72,947 against 3,789 bytes a second; with no delay 11.2 against 10.7 ms. A socket held for 100 s in a bot room stayed open (2.8 kB/s).
- **Tests.** `node tools/test-net.js` (child server on port 3195; the bench uses it too, so never run both at once). Its last part loads the page's whole script in a pretend browser (after the one in `tools/test-replay.js`), joins a real room on each link and presses keys.
- **Not tested.** A real browser: this was written without one. On Node 22 and later the tests use Node's own `WebSocket` (undici's, not this code) against the server and under the page's script, which is the nearest thing to a browser it has met; `EventSource` is a stand-in everywhere. Real tablets, a real network, a tablet that sleeps and wakes, and Render's proxy (if it does not pass the upgrade the page should fall back within 1.5 s). The old lane battler (`/events` in `server.js`) has no socket.

## Online play

- `POST /room` creates a room with a 4-letter code. `GET /events?room=CODE&id=CLIENT` is a Server-Sent Events stream (`hello`, `players`, `state`, `pending`, `spawn`, `cancel`, `reset`, `gone`). `POST /act` takes `start`, `reset` and `send` (strokes plus a PNG of the pad).
- The server is authoritative: it owns ink, runs the sim at 20 Hz and broadcasts state at about 10 Hz. Clients send strokes; every client rebuilds unit sprites from those strokes.
- First client in a room is Blue (side 0), second is Red (side 1), later ones spectate. A client id in sessionStorage lets a player reload and keep their side.
- Rooms are in memory, so a deployment must be a single instance.

## Tuning numbers (all in the SIM block)

Base health 500, match 90 s, ink max 100, refill 6/s (12/s in the last 30 s), ink cost = stroke length / 28. Unit speed and health were raised/lowered once because the first version stalemated in about 90% of simulated matches. The bot's units are 15% weaker than their ink cost; that number is a guess.
